## 1. جوهر المشكلة والدرس المستفاد من التدقيق الجنائي

أثبت التدقيق الجنائي الشامل بالأدلة الملموسة أن فشل الموظف الرقمي الحالي في إجراء محادثة طبيعية بسيطة عبر Telegram ليس مجرد خطأ برمجي منفرد أو عَرَض يمكن إصلاحه بترقيع سريع؛ بل هو **نتيجة حتمية لخلل معماري جوهري** في المحرك التحاوري القديم (`conversational_agent_engine.py`):
1. **مصادرة قدرات الذكاء الاصطناعي:** تحول المحرك إلى شجرة Regex صلبة وقوالب معلبة تعترض 85% من المحادثات، وتحظر على النموذج استدعاء أي أداة تنفيذية (`You CANNOT execute tools`).
2. **بتر الذاكرة القسري وتجويع السياق:** تحديد التاريخ بـ 8 رسائل أو 2,000 حرف، مما يصيب الوكيل بفقدان ذاكرة حتمي عند السؤال الرابع في أي محادثة واقعية.
3. **غياب التنفيذ المتين (Zero Durable Execution):** عدم وجود محرك لحفظ الحالة واستعادتها بعد الانقطاع أو انتظار الموافقات، مما يجعل الوكيل عاجزاً عن استكمال أي مهمة متعددة الخطوات.

**القرار القاطع:** التوقف الفوري عن ترقيع المحرك القديم، واعتماد استبداله بنواة حديثة تفاعلية.

## 2. ماذا تعلمنا من المشاريع المرجعية السبعة؟

| المشروع المرجعي | الإسهام المعماري الجوهري لمنصتنا |
| :--- | :--- |
| **LangGraph** | مخطط الجداول الثلاثة في PostgreSQL (`checkpoints`, `blobs`, `writes`) ونمط المقاطعة `interrupt()` والاستئناف المتين، مما يحل مشكلة انقطاع الجلسات وفقدان مسار المهام. |
| **Memento-Skills** | دورة تطوير وتقييم المهارات المزدوجة (`With-skill vs Baseline`)، والمصحح الصارم (`grader.md`)، والمحلل الموضوعي (`analyzer.md`)، والتدريب المعزول عبر `uv`، لتطبيق التطور المهني المستمر للوكيل. |
| **RagLeap Core** | هندسة الاستقلالية الصريحة (`off`, `semi`, `full`)، وتتبع التلويث لمنع تسريب البيانات (`Taint Tracking`)، وحوكمة الميزانيات، ونظام الرصد اليومي الذي يغذي خط "الأب الروحي". |
| **Microsoft Agent Framework** | معمارية ضغط الذاكرة الدلالي (`_compaction.py`) دون بتر قسري، وبطاقة الوكيل التعاقدية (`AgentManifest`)، وتأمين الموافقات ضد التلاعب بالمعاملات (`Anti-Tampering`). |
| **OpenAI Agents Python SDK** | آلية تسليم المهام بين الوكلاء المتخصصين (`Handoffs`) كأدوات يفهمها النموذج، وحواجز الحماية متعددة الطبقات (`Input/Output Guardrails`). |
| **Dify** | تشغيل الـ Function Calling المتكرر، وتحرير معاملات قاعدة البيانات (`session.commit(); session.close()`) قبل استدعاء الـ LLM لمنع تجويع مجمع الاتصالات (Connection Pool Starvation). |
| **n8n** | خطافات دورة حياة التنفيذ (`ExecutionLifecycleHooks`) وحجب الأسرار والبيانات الحساسة في السجلات. |

## 3. المعمارية المستهدفة المقترحة (Target Architecture Blueprint)

1. **نواة التشغيل (StateGraph Engine):**
   - محرك تفاعلي مبني على الرسوم البيانية الموجهة، يستدعي الأدوات عبر Function Calling الحقيقي، ويحفظ الحالة دورياً في PostgreSQL.
2. **الذاكرة المؤسسية رباعية الطبقات (4-Tier Enterprise Memory):**
   - ذاكرة محادثة مضغوطة دلالياً (`Compaction`).
   - ذاكرة حقائق دائمة عبر البحث الهجين في `pgvector` مفهرسة بـ `tenant_id`.
   - ذاكرة عمليات تتبع مسار المهام والخطوات المنجزة والمتبقية.
   - ذاكرة مهارات وإجراءات مهنية معتمدة بتنسيق `SKILL.md`.
3. **الأب الروحي المركزي (The Godfather):**
   - كيان رقابي مستقل يرتبط حصرياً بالمؤسس عبر تيليجرام.
   - يراقب صحة المنظومة، ورصد الانحرافات، وتحليل النواقص من واقع السجلات المركزية (Telemetry)، ويقدم تقريراً مسائياً يومياً بمقترحات التحسين المبررة.
4. **وحدات الأعمال الديناميكية (Dynamic Business Modules):**
   - توفير وحدات تشغيلية متكاملة (مثل المبيعات والتكلفة والمخزون) داخل المنصة للوكلاء المتخصصين، مع احتساب الأرباح النظيفة فقط عند توفر بيانات التكلفة الحقيقية.
5. **استمرار الحماية المتينة:**
   - الحفاظ على نمط صندوق الصادر (`Transactional Outbox`) وتشفير الأسرار المصادق (`AES-256-GCM`) وعزل المستأجرين الـ 54 جدولاً.

## 4. ما لا نوصي به قطعيًا (Strict Anti-Patterns)

1. **لا نوصي بالترقيع الموضعي:** الاستمرار في إضافة `if/else` أو تعابير Regex داخل `conversational_agent_engine.py` هو هدر للموارد وتكرار لنفس الأخطاء.
2. **لا نوصي باعتماد إطار عمل خارجي مغلق كبديل للمنصة:** تجنب استخدام Dify أو n8n كـ Core للمنصة بسبب القيود التجارية لتراخيصها وعدم توافقها مع عزل المستأجرين الـ 54 جدولاً لدينا.
3. **لا نوصي باحتجاز أقفال قاعدة البيانات أثناء استدعاء الذكاء الاصطناعي:** يجب تحرير الجلسة فوراً قبل انتظار زمن استجابة النموذج لتفادي انهيار الخادم.
4. **لا نوصي باحتساب أرباح وهمية:** منع أي وكيل مبيعات من تقديم أرقام أرباح تخمينية دون وجود فواتير تكلفة مسجلة في قاعدة البيانات.

## 5. مصفوفة المخاطر التشغيلية وخطة احتوائها

| الخطر المحتمل | درجة الخطورة | استراتيجية الاحتواء المعتمدة |
| :--- | :---: | :--- |
| **تعطل موصلات القنوات أثناء التبديل** | **High** | التبديل يتم خلف موجه القنوات؛ فجميع الرسائل الصادرة تمر عبر جدول `outbox_events` نفسه الذي لم يتغير. |
| **زيادة استهلاك التوكنات مع الذاكرة الموسعة** | **Medium** | تطبيق خوارزمية ضغط الذاكرة الدلالي (`_compaction.py`) لحصر السياق في حدود 4,000 توكن. |
| **تنفيذ أدوات خاطئة بواسطة النموذج** | **High** | تطبيق حواجز الحماية (`ToolInputGuardrail`) وخفض الأدوار الحساسة قسرياً لطلب موافقة المالك (`semi-autonomy`). |
| **انقطاع خادم قاعدة البيانات أثناء الحفظ** | **Medium** | المعاملات الذرية (`ACID Transactions`) والتراجع الكامل (Rollback) في حال فشل أي كتابة مرحلية. |

## 6. الخطوات التالية للتنفيذ الفعلي (Next Actionable Steps)

1. **اعتماد قرار المؤسس** بشأن بناء نواة `StateGraph Engine` المحلية الخفيفة وحسم قناة بوت الأب الروحي (`11_DECISIONS_AND_OPEN_QUESTIONS.md`).
2. **المرحلة 1 للتنفيذ:** إنشاء ترحيل Alembic لجداول الـ Checkpointing الثلاثة (`agent_checkpoints`, `agent_checkpoint_blobs`, `agent_checkpoint_writes`).
3. **المرحلة 2 للتنفيذ:** بناء مشغل الرسم البياني المستقل في `packages/engine/` مع ضاغط السياق الدلالي ومشغل الأدوات المهيكل.
4. **المرحلة 3 للتنفيذ:** تفعيل التوجيه المزدوج (Shadow Testing) لمقارنة المحركين في الخلفية.
5. **المرحلة 4 للتنفيذ:** التحقق الميداني الحقيقي عبر محادثات تيليجرام حية ومطولة مع مستأجر تجريبي للمؤسس.
6. **المرحلة 5 للتنفيذ:** إطلاق خدمة "الأب الروحي" وتفعيل التقرير المسائي اليومي وأرشفة المحرك القديم نهائياً.
